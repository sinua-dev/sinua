# Testing

## The layering

Correctness is proven once, at the Rust level, against frozen data — then each platform binding only needs to prove its *own* layer (the FFI round-trip), not re-derive engine correctness independently:

```
spec/orbs-golden.json     (frozen, vendored from upstream, never regenerated locally; sizes 64, 20)
spec/orbs-golden-32.json  (upstream's same engine, unmodified, at 32 -- scripts/oracle/README.md)
        │
        ▼
crates/core_engine/tests/golden.rs     — exhaustive: 9 states × 3 sizes × 4 timestamps = 108 cases,
        │                                 every dot/line field within 1e-4 tolerance
        ▼
packages/{ios,android,react-native}'s own tests   — thin: a handful of the same golden values,
                                                      checked through the real FFI boundary
```

If the Rust suite passes, the ported engine is correct. If a platform's thinner test also passes, that platform's *bridge* doesn't corrupt or misroute the data. That is a narrower and cheaper claim, and it is all that's needed once the engine itself is proven.

"Correct" above only covers the **9 ported states**. For every other state there is a second, weaker layer:

```
spec/sinua-golden.json  (frozen, generated BY THIS ENGINE, re-baselined only deliberately)
        │
        ▼
crates/core_engine/tests/sinua_golden.rs — 25 non-ported states × 2 sizes × 4 timestamps
        │                                     + 10 input-driven cases = 210 cases; dots, lines
        │                                     AND polylines within 1e-4
        ▼
platform parity — the SAME file, read by each binding (no hard-coded copies):
  packages/core   test/sinua-golden.test.mjs         all 210 cases through wasm (node)
  packages/ios    SinuaGoldenTests.swift             all 210 cases through UniFFI (simulator)
  packages/android SinuaGoldenTests.kt               all 210 cases through UniFFI/JNA (emulator)
  react-native    example/sinuaCheck.js + sinuaCheckpoints.json
                                                       4 checkpoints through the RN native module
```

## The Sinua golden set: a regression lock, not a correctness proof

Upstream's `spec/orbs-golden.json` is an **external oracle**. It was produced by a different implementation (`thinking-orbs`' TypeScript engine), and our port has to reproduce it. `spec/sinua-golden.json` is not an oracle. It was generated by this engine, so it can only ever say **"the output is unchanged since the baseline"**. It never says "the output is right". Whether a state looks right is still decided by its unit tests and by eye (contact sheets and the Studio).

This set exists to catch silent drift:
- a refactor that was meant to change nothing (e.g. the 2026-09-18 `bar` helper extraction)
- an engine change leaking into states it wasn't meant to touch
- later, cross-platform parity for the native FFI tests

This is the role Jest's snapshot docs describe (fetched, `jestjs.io/docs/snapshot-testing`): the test fails when output changes, and then "either the change is unexpected, or the reference snapshot needs to be updated". Snapshots add value alongside unit tests but don't replace them.

**What it freezes** (`cases()` in `tests/sinua_golden.rs` is the single source of truth):
- **Plain `frame()` for all 25 non-ported states:**
  - the 9 additive orbs, including `drifting` and `muted`
  - signal ×4, ring ×5, beacon ×5, core ×2
  - sizes 64 and 20 and times 0.6 / 1.7 / 3.3 / 5.1, which are upstream's own sizes and times; the file is ~0.9 MB
- **10 input-driven cases at 64 px, t = 0.6** that plain `frame()` never reaches:
  - ring `completing`/`stepping`/`measuring` with a fixed `progress` (a 0% ring is just a dot)
  - `tracking` with an overflowing lap
  - signal `signaling`/`waveform`/`metering` with 8 fixed audio bands, and `scrolling` with a fixed history buffer
  - beacon `reconnecting` with `quality: 0.66` and `broadcasting` with `level: 0.5`
- **The `resolved` preset** (mode / speed / opts) per state and size.

**Format:**
- Dot stride is **8** (upstream's 6 plus `saturation`, `hue`), because many of these states are coloured.
- Line stride 7, as upstream.
- Polylines are stored as `{style: [white, a, w, saturation, hue], points: [x, y, …]}`. Upstream has no polylines.
- Values are rounded to 6 decimals.
- Dots compare strictly first, with a nearest-neighbour fallback: the same z-sort tie-break reasoning as below, copied rather than shared, since `golden.rs` stays untouched.
- Lines and polylines are compared strictly.

**Guards:**
- `every_non_ported_state_is_frozen` fails if a listed state stops resolving, if a ported state sneaks into this set, or if a listed state has no case.
- `the_two_lists_together_are_every_pattern_the_engine_has` fails if `STATES` + `PORTED` is not *every* pattern the engine has. Adding a state to `STATES` used to be a rule written in a comment; this is the check. It compares against `parameter_catalog_json()` rather than the private `presets::STATES` (integration tests cannot reach those), and `catalog_pattern_names_match_the_presets` in `catalog.rs` pins the catalog to the presets — so the two together chain golden → catalog → presets, and whichever link breaks names the state.
- A test fails if the frozen file and `cases()` disagree.
- Verified by perturbation when the set was created: radar's dot spacing 4.5 → 4.6 failed with `scanning-64-0.6: dot count`, and matrix's unlit alpha 0x22 → 0x23 failed with `metering-64-0.6: dot[1] field 5`. Both were reverted.

**Re-baselining is deliberate. It is never a way to make a red test green.**

**Re-baseline log:**
- 1.0.0 (2026-09-18): the initial set, 210 cases.
- 1.1.0 (2026-09-18, Color system):
  - **Shape change:** the line stride goes 7 → 9 (`+saturation, hue`) and each case gets a `colorMode`.
  - **4 new material cases:** `connecting` coloured (lines included), `working` in fixed mode with a lightness bias, `searching` with a 3-stop gradient, and `connecting` with a gradient on its lines. These are the only cases that may use a ported state, because they freeze the post-process, not the geometry; a guard test enforces this.
  - A script diffed v1.0 against v1.1: **every pre-existing value is identical**, all old lines have `saturation` and `hue` equal to 0, and all old cases are `ink`.
  - The wasm, iOS and Android parity tests read the stride from `specVersion`. The RN checkpoints gained `colorMode` and the fixed-colour case.

```bash
SINUA_GOLDEN_WRITE=1 cargo test -p core_engine --test sinua_golden -- --ignored
```

Without the env var the generator panics instead of writing. After regenerating:
1. **Read the `digests` block, not the floats.** One line per case, named. Only the cases you meant to change should move.
2. Say in the commit message which states changed and why — the digest block is the list.

If cases you didn't mean to touch moved, that is the bug the set exists to catch.

**Why `digests` exists.** Step 1 used to say "review the JSON diff", and that review could not actually be performed. Measured on 2026-09-20: changing one constant in one pattern (`orbs/modes/aurora.rs`, radius `0.82` → `0.84`) moves **12 of 233** cases — the guarantee scoping correctly — but rewrites **17,254 lines**, and **0** of those hunks contain a case name, because the numbers sit deep inside arrays. So the step degraded to "regenerate and trust", which is what this file's header warns against. The same change now shows **12 named cases** in the digest block (`glowing-20-0.6`, `glowing-64-0.6-holo`, …). The vectors are untouched — four platforms' parity tests read them — and `digest_block_matches_the_vectors` recomputes every entry so the index cannot drift from what it indexes.

**A detail worth knowing if you ever compute your own digest.** The digest hashes the case **as the file stores it**, not as the writer held it in memory. One `history` override does not survive serde_json's serialise → parse round trip: the writer holds `0.9272994540441407`, the file parses back `…408`. The vectors are safe because `flat` rounds them through `r6`; the overrides map carries full f64 precision and is not rounded. The difference is 1 ULP, far below this set's `1e-4` tolerance, so no parity test can see it — but a digest taken before the write would permanently disagree with one taken after.

### Which set proves what

The two golden sets do not have the same standing, and it matters when you are deciding whether a re-baseline is legitimate:

- **`spec/orbs-golden.json` is an external oracle.** Its vectors come from a *different implementation* — upstream `thinking-orbs`' TS engine — so it can say the Rust port is **right**. Re-baselining it would mean abandoning the only independent check the project has. Don't.
  - **Size 32** (`spec/orbs-golden-32.json`, 2026-09-21): upstream's golden predates upstream's size 32, so these vectors come from a later upstream commit (`2015f0b`) through `scripts/oracle/extract-orbs-golden.ts`. That commit is the *same* oracle because, with the same harness at 64/20, it reproduces `orbs-golden.json` byte for byte. The README has both commands. Our port matched all 36 cases the first time. The gate fires when a 32 preset's speed, radius or count changes; a count change small enough to round to the same grid doesn't change the output, so it passes, correctly.
- **`spec/sinua-golden.json` is self-generated.** It was produced by this engine, so it can only say "unchanged since baseline", never "correct". It is a regression and cross-platform lock. Re-baselining it is legitimate when you meant the change — and the `digests` block is how you show you meant it.

That distinction was previously stated only in the two files' headers, where nobody deciding whether to re-baseline would see it.

**The writer is idempotent**, so step 1 is meaningful: regenerating without an engine change produces **no diff at all**. That was not true until 2026-09-20 — the checked-in file was the writer's output minus its final newline, so every regeneration showed a whole-file-tail change plus git's `\ No newline at end of file`, training the reviewer to wave the first diff through (`docs/code-health-engine.md` E6). It was fixed by running the writer once and proving the only change was that byte: `cmp` reporting `EOF` alone, the new file's first 1 145 577 bytes hashing to the old file's full hash, and `jq -S` canonical JSON identical on both. If you ever see a tail-shaped diff again, something reformatted the file — do not accept it as cosmetic.

### Platform parity against the Sinua set

Every binding checks the frozen file itself. The rules mirror the Rust checker: counts, then dots compared strictly with a nearest-neighbour fallback, then lines and polylines strictly, all within the file's tolerance. These checks only prove that each platform's float/libm and bridge reproduce the Rust output. They are not correctness.

- **Web / wasm** (`packages/core/test/sinua-golden.test.mjs`, `npm test`): all 210 cases through the same `frameWithOverrides` the web Studio uses.
- **iOS** (`packages/ios/Tests/CoreEngineTests/SinuaGoldenTests.swift`): all 210 cases through UniFFI. The test reads `spec/sinua-golden.json` through `#filePath` instead of a SwiftPM resource, because `Bundle.module` needs the file inside the test target, which would mean a copy that can drift. Simulator runs can see the host file. Where the file can't be read, the test `XCTSkip`s with a message.

## The z-sort tie-break problem

`finalize_frame` (see [`engine.md`](engine.md)) sorts dots by `z` before returning them. For most modes this is a normal, well-separated sort. For the `breathing` state (`ring` mode, face-on) it is not: by construction, the projected `z` of every dot is mathematically ~0 — true zero plus sub-ULP floating-point noise from the trig chain that produced it. That noise's *sign* depends on exactly how `sin`/`cos` round their last bit, which differs between V8 (the golden vectors' source) and Rust's `libm` — so two dots with truly-tied z can land in a different (but equally valid) stable-sort order across platforms.

This was diagnosed, not guessed at: an independent Python re-implementation of the same formula reproduced the identical mis-ordering against the golden JSON, which ruled out a Rust-specific bug and confirmed it as a genuine cross-platform floating-point non-determinism in a degenerate (near-zero) sort key.

**The fix lives in the test, not the engine.** `crates/core_engine/tests/golden.rs` compares dots in strict index order first (fast path, and gives a precise error location for a *real* mismatch); if that fails, it falls back to a **greedy nearest-neighbor match** — pairing each computed dot with its closest not-yet-claimed golden dot across all 6 fields — before concluding there's an actual value error. A plain sorted-tuple comparison was tried first and rejected: `ring`'s parallel lanes have several near-identical dots with near-tied *x* too, which scrambled a tuple sort's pairing the same way, and on a mode with no z-degeneracy (`globe`) it produced an outright false failure from bad pairing alone, not a real one.

## Two more comparison-fragility bugs, found the same way

Both were caught by *running the thing*, not by code review — the pattern is worth internalizing when adding a new cross-language comparison:

1. **Swift's `[String: Any]` does not preserve key order.** `packages/react-native/ios/SinuaCore.swift`'s `dictionary(from:)` builds JS-facing objects from a Swift dictionary literal; two structurally identical `OrbFrame`s can bridge to JS objects with their keys enumerated in a different order. `packages/react-native/example/App.tsx`'s smoke test originally compared results with `JSON.stringify(a) === JSON.stringify(b)`, which is not a valid equality check here — it failed intermittently on iOS (not Android, where the equivalent Kotlin path happened not to trigger it) for reasons that had nothing to do with the actual values being wrong. Fixed by comparing field-by-field instead of via serialized-string equality.
2. **`NSDictionary` isn't directly iterable as `(key, value)` pairs in Swift** the way a bridged `[String: Any]` is. `resolveFrameWithOverrides`'s first draft iterated the raw `NSDictionary` parameter directly, which silently produced zero entries instead of a type error — overrides appeared to have no effect, discovered via a temporary `NSLog` dump of the parsed map showing it was empty. Fixed by casting to `[String: Any]` before iterating.

Neither is a Rust engine bug; both are native-bridge-layer bugs that only surfaced by running real code on a real simulator/emulator and reading the actual output — see [`lessons-learned.md`](lessons-learned.md) for the general pattern (stale-app-reload masking a fix, in particular).

## CI

`.github/workflows/ci.yml` (GitHub Actions) runs on every push and pull request. It has **four** main jobs: two Linux jobs on `ubuntu-latest` (`rust`, `web`) and two native legs, `ios` and `android` (added 2026-09-19), plus the `materials` comparison job that needs all three. There was a separate `site` job until the first Actions run (2026-09-21); see below.

- **`rust`**
  - `cargo fmt --all --check`
  - `cargo clippy --workspace --all-targets -- -D warnings`
  - `cargo test --workspace`: unit tests, upstream's `golden.rs`, and `sinua_golden.rs`. The generator stays `#[ignore]` and env-gated, so CI can never re-baseline.
- **`web`**
  - Codegen: `generate.mjs --check` (the generated files' bytes), `api-snapshot.mjs` (their public contract: names, types, parameter order, pattern ids; see [`fx-view.md`](fx-view.md) *Typed components*), then `scripts/codegen/test/*.test.mjs`.
  - `packages/core`: `npm ci` → `npm run build` (wasm-pack + tsc) → `npm test`. That covers the reactive helper, the 210-case wasm parity test, the RN checkpoint sync and whatever else lands in `test/`.
  - `apps/examples/web-component`: `npm ci` → `npm run build` → `npm run typecheck` → Playwright Chromium + `npm run smoke`. The five framework apps (HTML, Vue, Svelte, Solid, Angular) are the **only automated consumer of `<sinua-view>` custom-element registration** — the docs site uses `mount()`, and the snippets that `import "@sinua/web/element"` are type-checked, never executed. That path has broken silently before: `sideEffects: false` once reduced the import to a 131-byte bundle with the tag never upgrading. They had no CI job at all until 2026-09-20.
  - Core must build first, because the examples depend on it via `file:`. That ordering is why the examples live in this job instead of their own: a separate job would have to rebuild the wasm engine or carry both `dist/`s across as artifacts.

**Pinning:**
- The toolchain comes from `rust-toolchain.toml`, so CI and local builds match. The install step is `rustup show active-toolchain || rustup toolchain install`, then an explicit component and target add. rustup 1.28.0 stopped installing the toml toolchain implicitly, and 1.28.1 restored it. This form works either way, per the rustup blog.
- The toml also lists iOS/Android targets, which the runner may download. That costs a little time but is harmless.
- `wasm-pack` 0.13.1 is installed with `taiki-e/install-action`. It replaces the unmaintained `jetli/wasm-pack-action`.
- Node 24, with npm caching keyed on both lockfiles.

**Local counterpart:** `scripts/ci-local.sh` runs the same commands in the same order and fails fast. Keep the two files in sync. The script uses `npm ci`, which reinstalls `node_modules`, so **run it on a clean copy** of the tree, not beside a running dev server. That is how it was verified when added: an rsync of the working tree without `node_modules`, `target`, `dist`, `pkg` and build dirs, run end to end, all green.

**It is a subset by default, and says so.** The bare `scripts/ci-local.sh` covers the `rust` and `web` jobs, including the React Native JS leg that CI also runs unconditionally; `--native`, `--site` and `--examples` add the rest, and **`--all` runs every job**. When anything was skipped the final line names it, instead of the unconditional "CI mirror: all green" it used to print after skipping three CI jobs. **`--list` prints the plan and runs nothing** — the cheap way to see what a given invocation would and would not cover.

Two differences from CI that no flag removes, both environmental: CI pins `wasm-pack` while the script uses whatever is on `PATH` (it warns when the versions differ), and CI installs Playwright's Chromium while the local smokes use the browser you already have, or `$SINUA_CHROME`.

**Not verified yet:** the GitHub-hosted specifics (the runner image, action versions resolving, cache behaviour). The repo had no commits or remote when this was written, and pushing is the owner's call.

### The docs site (checks and build, both in the `web` job)

- **In the `web` job (and the default local run),** right after `packages/core`'s tests:
  - `node scripts/docs/gen.mjs --check`: the 🤖 MDX partials in `apps/site/content/generated/` match `spec/parameters.json`, the FX Spec schema, and the engine's real diagnostics for `scripts/docs/diagnostics-cases.json`;
  - `node scripts/docs/check-snippets.mjs`: every `apps/site/snippets/spec/*.fxspec.json` resolves with zero diagnostics (base, every state, both power states), and `snippets/ts/*.ts` type-check. It also runs the **reverse** check — is every snippet reachable from a page? — added 2026-09-20. A snippet counts as referenced when an MDX `<include>` **resolves** to it (the path is relative to the page, so it is resolved, never substring-matched) or when its `snippets/`-relative path appears as a quoted string in the site's code or MDX, which is how `<Demo spec="spec/x.fxspec.json" />` reaches one. Six compile-harness files (`Package.swift`, `Package.resolved`, `android/build.gradle.kts`, the three `tsconfig*.json`) are allow-listed in the script with a reason each, and an allow-list entry whose file has disappeared is itself a failure.

    **Match on the path, never on the basename — and record when you measured.** Both halves of that sentence come from how this check came about. Three sessions counted orphans in the same tree on 2026-09-20 and got 13, 10 and 12; the count is now 0. Most of that gap was **the tree moving**, not the measuring: six MDX pages were wired up at 16:16, and between them they reference eleven of the twelve files that had been listed. One file was a genuine matcher miss — `spec/ring-progress.fxspec.json`, reached by `<Demo spec="spec/ring-progress.fxspec.json" />` from a page untouched since the previous night, where the path is quoted *without* the `snippets/` prefix.

    So the two rules the checker encodes: a loose matcher over-reports references, because basenames like `tsconfig.json` occur everywhere in any tree; and a matcher that only looks for `snippets/<path>` under-reports, because it misses the `<Demo spec>` form. The check exists so the number is computed rather than estimated, and so that a count taken five minutes apart means the same thing.
- **The site build** (`--site` locally; the end of the `web` job in CI) runs `apps/site`'s own `npm ci`, then `next build`, the static export. It compiles every MDX page and every `<include>`, so it catches content errors the checks above don't, such as frontmatter YAML. It has its own install, but it depends on `@sinua/{web,core,snippets}` through `file:`, so it needs their `dist/` (core's wasm too) and their own `node_modules`. That's why it runs in the `web` job after those packages are built. As a separate job on a clean runner it failed the first Actions run with `Can't resolve '@sinua/core'`. `ci-local.sh --site` had always run it last, so it passed locally. Locally, run it on a copy, not beside a running `next dev`, since both use `apps/site/.next`.

### The native legs (`ios`, `android`)

Both jobs run a script from `scripts/`, the same one `scripts/ci-local.sh --native` runs. The workflow and the local mirror can't drift on what gets built or which tests run.

- **`ios`** (`xcode-27`), `scripts/ci-native-ios.sh`:
  - **When it runs:** every push to `main`, every manual run (`workflow_dispatch`), and other pushes / PRs only when they touch iOS-specific files. The `changes` job decides; its log lists the changed files and the reason. macOS minutes count ~10× against the Actions quota: on 2026-09-21 this job was ~2,800 of the day's ~3,200 counted minutes and used up the month's free quota. An engine or spec change on a work branch is checked on iOS when it reaches `main` (and locally with `scripts/ci-local.sh --native`). When `ios` is skipped, `materials` is too, because it needs the iOS renders.
  - `packages/ios/build.sh` rebuilds the Swift bindings and `core_engineFFI.xcframework`;
  - then `xcodebuild test -scheme CoreEngine-Package` with `-only-testing:` for **all four** test targets (`CoreEngineTests`, `SinuaVoiceTests`, `SinuaTests`, and `SinuaGeminiLiveTests`, added 2026-09-19, which uses in-process localhost fakes, no network or audio) and `-collect-test-diagnostics never`. The filter is not optional: an unfiltered run hung in `simctl diagnose`, and the diagnostics flag stops a failing test from triggering the same sysdiagnose.
  - **Simulator:** `$IOS_SIM_UDID` if set; otherwise an already-booted iPhone; otherwise the first available iPhone on the newest iOS runtime. The script never shuts down or erases a simulator, because locally the simulator is shared between sessions.
  - Then a compile-only `xcodebuild build -scheme SinuaLiveKit -destination 'generic/platform=iOS Simulator'` of `packages/ios-livekit`. That's the separate LiveKit glue package; it pulls `client-sdk-swift` and its WebRTC binary. Its tracker logic is tested in `SinuaVoiceTests`. In CI, `$SPM_CACHE_DIR` points SwiftPM's clones (`-clonedSourcePackagesDirPath`) at `.spm`, cached on `packages/ios-livekit/Package.resolved`.
  - **Image:** `xcode-27` (actions/runner-images, labelled *preview*) carries Xcode 27.0 `27A266a`, the exact build used locally, and an iOS 27.0 runtime. It has no Rust, so the job installs rustup and then the pinned toolchain. It was `macos-15` (default Xcode 16.4) until the first Actions run (2026-09-21). There, Swift 6.1's `swift format` couldn't decode `.swift-format` (written by the 6.4 toolchain), and the lint gate failed every file before anything compiled. The lint gate's output depends on the toolchain's `swift format` version, so the CI image has to match local.
- **`android`** (`ubuntu-latest` with KVM), `scripts/ci-native-android.sh`:
  - **`build`:**
    - `packages/android/build.sh` builds the Kotlin bindings and the jniLibs for all four ABIs. The script picks the host bindgen library by OS: `.dylib` on macOS, `.so` on Linux.
    - Then the JVM tests: `:testDebugUnitTest` (voice golden parity), `:sinua-view:testDebugUnitTest` (FxView performance) and `:sinua-gemini:testDebugUnitTest` (the Gemini Live session against localhost fakes; OkHttp 4.12.0).
  - `build` also runs `:sinua-livekit:assembleDebug`, a compile of the LiveKit glue module. It has no tests of its own, and the JitPack repo it needs is already content-filtered in `settings.gradle.kts`.
  - **`connected`:** `:connectedDebugAndroidTest` (both golden sets, FX Spec) and `:sinua-view:connectedDebugAndroidTest` (the FxView render test), inside `reactivecircus/android-emulator-runner@v2`.
  - **Emulator:** API 35, `google_apis`, `x86_64`. That's the same API level and tag as the local `Nutp_Test` AVD; the jniLibs ship an x86_64 slice.
  - **KVM:** enabled with the udev rule from the runner action's README. Linux + KVM is its recommended setup, faster and cheaper than macOS runners.
  - **AVD cache:** the README pattern. `actions/cache` on `~/.android/avd`; a snapshot-generating first pass on a miss; tests then run with `-no-snapshot-save`.
  - **Image:** the ubuntu image provides NDK 27 at `$ANDROID_NDK_HOME` (which `build.sh` honours) and JDK 17 as the default (AGP 8.7.3).
  - `cargo-ndk@4.1.2` comes via `taiki-e/install-action`. It's not in that action's own list, so the action falls back to cargo-binstall.
- **Caches:**
  - `Swatinem/rust-cache@v2` on both jobs.
  - `gradle/actions/setup-gradle@v6` on `android`. It writes the cache only from `main`; other branches read it.
  - SwiftPM: `actions/cache` on `.spm` for `packages/ios-livekit`'s clones. `packages/ios` itself has no remote dependencies.
- **Local mirror:** `scripts/ci-local.sh --native` runs the Linux steps, then the two native scripts. For Android it reuses a device already listed by `adb devices`. Otherwise it boots `Nutp_Test` headless (`$ANDROID_AVD` overrides the name), with both `ANDROID_HOME` and `ANDROID_SDK_ROOT` pointing at the emulator's SDK root (the emulator reads `ANDROID_HOME` first, and the Gradle one has no system image for this AVD). It polls `sys.boot_completed` for up to 6 minutes, never with a bare `adb wait-for-device`, and on exit kills **only the emulator pid it started**. That boot branch was proven end to end on 2026-09-19: a clean rsync copy with no device attached booted the emulator, all native legs passed (EXIT 0), and no emulator was left running. Without `--native`, the script is the fast Linux-only run it always was.

**Not yet run on GitHub:** the native jobs are linted (actionlint 1.7.12) and their scripts were verified locally, but the runner-side specifics (KVM on the hosted runner, AVD creation, the macOS simulator pick) are proven only by a real push. Pushing is the orchestrator's call, with the user's OK.

**Still manual:** the RN example on both platforms. For RN, the on-screen PASS line has to be read through logs (`adb logcat`, simulator `log show`). It's the next native leg worth adding.

**Native vendor voice sources (2026-09-19, voice-adapters):** `scripts/ci-native-ios.sh` runs `SinuaGeminiLiveTests` + `SinuaElevenLabsTests` (in-process fake servers, fake audio devices) and compile-only builds `SinuaLiveKit` and `SinuaOpenAI` (separate packages carrying vendor binaries). `scripts/ci-native-android.sh build` runs `:sinua-gemini` / `:sinua-elevenlabs` / `:sinua-openai` JVM tests and assembles `:sinua-livekit` / `:sinua-openai`. No test opens real audio; the opt-in `AVPcmAudioDeviceSmokeTests` (`TEST_RUNNER_SINUA_AUDIO_SMOKE=1`) must never be set in CI.
