# iOS / Swift

## `packages/ios` — the Swift Package

A local Swift Package (no remote registry) wrapping a UniFFI-generated Swift binding around a native `core_engine` build.

> **No renderer in this package itself.** `packages/ios` proves `frame(state:size:t:)` returns correct data (see *Testing* below) — it does not draw anything; a consumer gets `OrbFrame` (dots/lines) and paints it. The SwiftUI renderer is the `Sinua` product (*Rendering* below): the paint contract (`spec/orbs-spec.json`) transcribed into SwiftUI `Canvas`.

```
packages/ios/
├── Package.swift
├── core_engineFFI.xcframework/     # gitignored, regenerated by build.sh
├── Sources/CoreEngine/
│   └── core_engine.swift            # gitignored, UniFFI-generated, regenerated by build.sh
└── Tests/CoreEngineTests/
    ├── GoldenTests.swift            # hand-written, tracked (upstream vectors, smoke)
    └── SinuaGoldenTests.swift     # hand-written, tracked (all 210 spec/sinua-golden.json cases)
```

### Build pipeline (`build.sh`)

```bash
packages/ios/build.sh
```

1. `cargo build -p core_engine -p uniffi-bindgen` — a **host** (macOS) build, only so `uniffi-bindgen` has a compiled dylib to introspect.
2. `cargo run -p uniffi-bindgen -- generate --library target/debug/libcore_engine.dylib --language swift --out-dir bindings/swift` — produces `core_engine.swift`, a C header, and a modulemap.
3. `cargo build -p core_engine --release --target {aarch64-apple-ios, aarch64-apple-ios-sim, x86_64-apple-ios}` — three real device/simulator builds.
4. `lipo -create` the two simulator slices (`aarch64-apple-ios-sim` + `x86_64-apple-ios`) into one universal simulator library — an XCFramework needs exactly one slice per platform-variant, and "iOS Simulator" covers both Apple Silicon and Intel Macs.
5. `xcodebuild -create-xcframework` combines the device slice and the universal simulator slice, embedding the UniFFI-generated header, into `core_engineFFI.xcframework`.

The Rust targets (`aarch64-apple-ios` etc.) are listed in the workspace-root `rust-toolchain.toml`, not just installed ad hoc — this matters because this repo pins its own toolchain (`channel = "1.98.1"`) separately from whatever `rustup default` points at, and `rustup target add` without `--toolchain` adds to the *default* toolchain, not this repo's pinned one. (Cost an hour of "why can't it find std" confusion once — see [`../lessons-learned.md`](../lessons-learned.md).)

### Consuming the package

`Package.swift` declares a `binaryTarget` (the xcframework) and a regular `target` (the vendored Swift source) that depends on it. A consuming Xcode project adds this as a local Swift Package dependency (`File → Add Package Dependencies → Add Local...`), pointing at `packages/ios`.

### Voice: the `SinuaVoice` product

A second product in the same package, with no dependency on `CoreEngine`:
the native audio pipeline (mic and test tone → the engine's voice opts).
An app that never uses the mic just doesn't add it.

```swift
import CoreEngine
import SinuaVoice

let source = LocalMicVoiceSource()            // or TestToneVoiceSource(); needs NSMicrophoneUsageDescription
let voice = VoiceOverrides.bind(source)        // Orb: options.bandEaseRate = .infinity
try await source.connect()                     // asks mic permission; throws VoiceSourceError.permissionDenied
// per frame:
let frame = frameWithOverrides(state: "speaking", size: 64, t: t, overrides: knobs.merging(voice.overrides(dt: dt)) { $1 })
```

The byte spectrum, band math and `VoiceOverrides` are checked against
Chrome/Web's own output by `Tests/SinuaVoiceTests` (`spec/voice-golden.json`,
`xcodebuild test -scheme CoreEngine-Package -only-testing:SinuaVoiceTests
-destination 'platform=iOS Simulator,…'`). Design, parity method and
permissions are in [`../audio-pipeline.md`](../audio-pipeline.md#native-iosandroid-mic--test-tone-built-spec-exact-parity-with-web).

### Rendering: the `Sinua` product

A drop-in SwiftUI view. It depends on `CoreEngine` and on the voice *types*
(`VoiceSource`, `VoiceOverrides`, `AgentState`, in the internal `SinuaVoiceTypes`
target, which has no audio I/O and which `Sinua` re-exports), **not** on `SinuaVoice`:
an app that only draws doesn't link the microphone code (measured on a `Sinua`-only
package: 124 microphone-related symbols before the split, 0 after;
`scripts/ci-native-ios.sh` fails if `Sinua` reaches `SinuaVoice`). It holds the
paint contract (`FxPaint`). The Studio's `OrbPaint` is now a
typealias of it.

```swift
import Sinua
FxView(spec: specJSON, voice: micSource)     // or FxView(state: "speaking")
```

It's built on `TimelineView(.animation)` + `Canvas`. It pauses on
disappear and in the background, and it follows `colorScheme` and
`accessibilityReduceMotion`. `Tests/SinuaTests` covers bitmap parity
with the old Studio painter and the spec math against `frameFromFxSpec`. See
[`../fx-view.md`](../fx-view.md).

### Testing

`Tests/CoreEngineTests/GoldenTests.swift` is a real `XCTest` target, run via:

```bash
xcodebuild test -scheme CoreEngine-Package -only-testing:CoreEngineTests -destination 'platform=iOS Simulator,name=iPhone 17'
```

This runs on an actual iOS Simulator (not a JVM-style unit test host) and exercises the real FFI boundary: Swift → C → Rust → C → Swift. It checks specific values from `spec/orbs-golden.json` plus a `frameWithOverrides` sanity check. `SinuaGoldenTests.swift` additionally checks every case of `spec/sinua-golden.json` (the 25 non-ported states), reading the repo file through `#filePath`; `FxSpecTests.swift` renders every `spec/examples/*.fxspec.json` the same way ([FX Spec](../fx-spec.md)) (see [`../testing.md`](../testing.md#platform-parity-against-the-Sinua-set)). Neither is a full re-run of the Rust golden suite (that's already proven at the Rust level; this only needs to prove the *binding* round-trips values correctly). See [`../testing.md`](../testing.md) for the layered-testing rationale.
