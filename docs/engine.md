# The `orbs` engine

## Provenance

9 of the 18 states in `crates/core_engine/src/orbs/` (the ones listed as ported in *States and modes*, below), plus `orbs::core`'s shared projection, Fibonacci lattice and value noise, are a line-by-line Rust port of the geometry engine from [`thinking-orbs`](https://github.com/Jakubantalik/Libraries.dev), a package by Jakub Antalik, MIT-licensed (`third_party/thinking-orbs/LICENSE`). "Port" means transcription, not reinterpretation: each Rust mode file carries a comment pointing at its TypeScript source (`thinking-orbs/src/engine/*.ts`), and correctness is proven by matching upstream's own frozen test vectors (`spec/orbs-golden.json`) rather than by independently re-deriving the math. When touching `orbs::core` or any `orbs::modes::*` file, keep it a faithful transcription — a "Rustified" rewrite would sever that provenance and the golden-vector proof along with it.

Two files are vendored verbatim from upstream and never hand-edited:
- `spec/orbs-spec.json` — the design-time spec: enums, base profiles, preset values, scaling rules, the paint contract.
- `spec/orbs-golden.json` — 72 frozen test cases (9 states × 2 sizes × 4 timestamps), each with the exact expected dot/line list to 6-decimal precision.
- `spec/sinua-golden.json` — 210 frozen cases for the 25 **non-ported** states (dots, lines and polylines). They were generated by this engine, so they are a **regression / cross-platform lock, not a correctness proof**. See [`testing.md`](testing.md#the-Sinua-golden-set-a-regression-lock-not-a-correctness-proof).

**What math is actually in the ported modes** (the original plan anticipated curl noise, Verlet integration, and quaternion rotation — none of that exists in any of the 9 ported modes): a Fibonacci sphere lattice (`fib_dir`), a simple hash-based value noise (`vnoise`/`hash_d` — not Perlin or Simplex), and a shared spin/tilt/orthographic projection (`Proj`) instead of quaternions — gimbal lock was never a real risk at this scale. If a future family genuinely needs spring physics or vector-field noise, `liquid-gooey` (see [*Other families considered*](#other-families-considered)) is the one upstream candidate that actually has it — don't assume the ported modes' math generalizes to that need. (One non-ported mode, `aurora`, does use real gradient noise — see *Additive capabilities beyond the port*, below.)

If upstream ever ships a new tuning pass, the right move is re-vendoring both files and re-running `cargo test`, not hand-patching values.

## States and modes

Each of the engine's "states" (the public API surface -- what a caller asks for) maps to one internal "mode" (the geometry function that actually draws it). 9 of the 18 below are the ported set golden-tested against `spec/orbs-golden.json`; the other 9 are additive, see *Additive capabilities beyond the port*, below.

| State | Mode | File | What it looks like |
|---|---|---|---|
| `working` | `orbits` | `modes/orbits.rs` | Particles running tilted orbits, ghost paths, no nucleus |
| `searching` | `globe` | `modes/globe.rs` | Lat/long dot field, a scan meridian sweeps |
| `solving` | `rubik` | `modes/rubik.rs` | Bands twist in quarter turns, scramble → solve, repeat |
| `listening` | `wave` | `modes/wave.rs` | A waveform rolls through concentric rings |
| `connecting` | `web` | `modes/web.rs` | A constellation wires itself; the only mode that emits `Line`s |
| `weaving` | `braid` | `modes/braid.rs` | Three strands plait around the sphere |
| `composing` | `ribbon` | `modes/ribbon.rs` | An undulating sash rides a great circle |
| `breathing` | `ring` | `modes/ribbon.rs` | **Shares `ribbon`'s geometry** — the `faceOn` opt switches a tilted sash into a face-on morphing ring. Confirmed against upstream's `registry.ts` (`ring: frameRibbon`), not assumed. |
| `shaping` | `morph` | `modes/morph.rs` | A dotted outline cycling circle → triangle → square |
| `glowing` | `aurora` | `modes/aurora.rs` | **Not a port.** A colored nebula cloud on a sphere, perturbed by real 3D gradient noise (`core::perlin3`). See *Additive capabilities beyond the port*, below. |
| `drifting` | `webflow` | `modes/webflow.rs` | **Not a port.** A deliberate near-twin of `connecting`/`web` — identical preset, opts, and painter, with node wander driven by `perlin3` instead of `vnoise`. Exists to A/B the two noise functions with nothing else changing; see the mode's own header comment. |
| `speaking` | `spectrum` | `modes/spectrum.rs` | **Not a port.** A discrete circular-EQ ring — fixed angular bars whose height jumps on a fixed cadence, unlike `wave`'s smooth continuous roll. Fills a real gap: `listening` covers input, nothing covered the agent actively talking. From [`effects-research.md`](effects-research.md)'s "Spectrum bars" proposal. |
| `confirming` | `sonar` | `modes/sonar.rs` | **Not a port.** A periodic expanding "ping" ring (adapted from the research proposal's one-shot idea to fit `frame(state, size, t)`'s stateless-`t` API — see the mode's header). Reads as "received"/"done", the only mode built around a discrete pulse rather than a continuous field. |
| `initializing` | `warp` | `modes/warp.rs` | **Not a port.** A depth-motion starfield tunnel — dots spawn near center and streak outward to the silhouette edge, then recycle. Every other mode moves dots tangentially on a fixed-radius shell; this is the only one with genuine radial depth throughput. Reads as "spinning up" (session cold start). |
| `calibrating` | `chladni` | `modes/chladni.rs` | **Not a port.** Fixed Fibonacci-lattice dots, brightness modulated by a cheap sum-of-cosines standing wave whose mode numbers snap (not drift) to a new pair on a fixed cadence — a kaleidoscope-like "settling into resonance," the cymatics metaphor. |
| `progressing` | `eclipse` | `modes/eclipse.rs` | **Not a port, and functionally new, not just visually.** A day/night terminator sweep driven by an actual `progress: 0..1` opt (not elapsed time) — the first *determinate* state; every other mode (ported or additive) is indeterminate. Dark-side dots are dimmed, not removed. |
| `concluding` | `crystallize` | `modes/crystallize.rs` | **Not a port.** Dots drift loosely (borrowing `web.rs`'s value-noise technique) around their resting vertex of an icosahedron/octahedron, periodically pull into exact rigidity (edges drawn as `Line`s via nearest-neighbor topology, not a hand-typed edge list — see the mode's header), hold, then release. Alternates polyhedra each cycle. |
| `muted` | `hush` | `modes/hush.rs` | **Not a port, and the first *negative/attention* state.** A dimmed, **still** (fixed camera, no spin), grey-or-tinted Fibonacci lattice with an optional slow breathing pulse (`pulseAmplitude`, `0` = fully static) — the "mic muted / connection lost / permission denied" resting pose. Mirrors the pattern Google Nest ("4 solid orange lights: the microphone is off") and Amazon Echo (solid red ring) share: active states animate, muted holds still in one flat color. Grey by default; `saturation`/`hue` give Echo red (8) or Nest amber (~35). Composes with the `muted` opts *flag* (`primitives::apply_muted`, which dims any state in place). `beacon` may later generalize this — see the mode's header. |

Every mode shares `finalize_frame(dots, lines, r_min)` — drops invisible marks (alpha < 0.02), clamps radii to the mode's floor, and **z-sorts** dots far-to-near into draw order. This is the one place with a genuine cross-platform numerical footgun — see [`testing.md`](testing.md#the-z-sort-tie-break-problem). It lives in `crates/core_engine/src/primitives.rs`, not `orbs/core.rs` — see [`architecture.md`'s *family pattern*](architecture.md#the-family-pattern) for why it (and `Dot`/`Line`/`OrbFrame`/the noise functions) moved to a family-agnostic module once `signal` (see [`signal.md`](signal.md)) needed them too. `OrbFrame` also carries a `polylines` list (`primitives::Polyline`, a continuous round-capped stroke; draw order is polylines, then lines, then dots), attached via `OrbFrame::with_polylines` by the modes that emit them — only `signal`'s today; every `orbs` mode leaves it empty, so nothing here touched the golden suite. See [`signal.md`](signal.md#the-polyline-primitive-why-signal-needed-one) for why it exists. What's left in `orbs::core` is genuinely sphere-specific: `Proj` — the shared spin/tilt/orthographic projection every `orbs` mode uses to place points on screen — and `fib_dir`, the Fibonacci sphere lattice.

## Additive capabilities beyond the port

Two things in `orbs::core` are not part of the `thinking-orbs` port and exist
only for `aurora` (`glowing`), the one mode with no upstream equivalent.
Both were added after a research pass (`docs/effects-research.md`) surveyed
what a second family would actually need and found these were the two
structural gaps: no color, and only hash-based value noise. Both are purely
additive — every one of the 9 ported modes is unaffected, which is exactly
why this didn't touch `spec/orbs-golden.json` or need re-vendoring:

- **`Dot.saturation` / `Dot.hue`** — every ported mode's `Dot` literal ends
  in `..Default::default()`, which resolves these to `0.0` (achromatic),
  so `crates/core_engine/tests/golden.rs`'s comparison — which only reads
  `x, y, z, r, white, a` (`DOT_FIELDS`) — never sees them and the golden
  suite is untouched. Every platform's paint contract (`drawFrame.ts`'s
  `ink()` and its Swift/Kotlin ports — see the note below) branches to HSL
  rendering only when `saturation > 0`.
- **`core::perlin3`** — real 3D gradient noise (Ken Perlin's "improved
  noise" structure: fade curve, gradient dot products, trilinear
  interpolation), proven by unit test (not a golden vector — nothing to
  port against): at an exact integer lattice point every gradient
  dot-product is exactly zero regardless of the permutation table's
  contents, which is what `core.rs`'s `zero_at_integer_lattice_points` test
  checks. `vnoise`/`hash_d` are untouched and every ported mode keeps using
  them — `perlin3` is additive, not a replacement. `webflow.rs` (`drifting`)
  is a deliberate near-copy of `web.rs` (`connecting`) with only the noise
  call swapped, for a controlled A/B comparison in the Studio.
  **Measured, not assumed, to be cheaper, not more expensive:**
  `core.rs`'s `perf_vnoise_vs_perlin3` test (`#[ignore]`d — run explicitly
  with `cargo test -p core_engine --release -- --ignored --nocapture
  perf_vnoise_vs_perlin3`) found `perlin3` at roughly **0.45x** `vnoise`'s
  cost per raw call (19ns vs. 43ns) and the whole `drifting` frame at
  **0.91x** `connecting`'s (both at size 64, nodeN 30). The reason:
  `vnoise` calls `hash_d`, which calls `sin()` (a transcendental function)
  four times per sample; `perlin3` only does permutation-table lookups and
  multiply-adds, no trig at all. "More sophisticated algorithm" turned out
  not to mean "slower" here — don't assume it does elsewhere either without
  measuring.

Six more states (`speaking`/`spectrum`, `confirming`/`sonar`,
`initializing`/`warp`, `calibrating`/`chladni`, `progressing`/`eclipse`,
`concluding`/`crystallize`) followed, one per new-shape concept surveyed in
`docs/effects-research.md`'s "New `orbs` modes" section — all six proposed
there are now built. None needed a new primitive (`Dot`/`Line` and the
color fields above were enough for all of them); none have a golden vector,
same tradeoff as `aurora`/`webflow`. Two are worth calling out specifically:
`eclipse` is the one *functionally* new addition in the whole set — every
other state (ported or additive) is indeterminate ("something is
happening"); `eclipse`'s `progress: 0..1` opt makes it the first
determinate ("N% done") state, threaded through the existing
`frame_with_overrides` entry point rather than a new API. `crystallize`'s
icosahedron/octahedron edge topology is derived at runtime by connecting
each vertex to its nearest neighbors by distance, not from a hand-typed
edge-index list — the same "generate, don't hand-transcribe" reasoning as
the Perlin permutation table above, checked by `crystallize.rs`'s topology
tests (30 edges/degree 5 for the icosahedron, 12/degree 4 for the
octahedron — the well-known properties of those two solids).

**Color renders on every platform now.** This was a Web-only capability for
a while (the native Studios had regenerated their FFI bindings before the
color channel existed, and their paint-contract ports drew grayscale ink).
The `Polyline` work (see [`signal.md`](signal.md)) regenerated every
binding and re-ported the paint contract to `OrbCanvasView.swift` /
`ImageExport.swift` and `OrbCanvas.kt` / `ImageExport.kt`, carrying the
`ink()` HSL branch along. The RN bridge's JS-facing `Dot` carries
`saturation`/`hue` as well. What the native Studios still lack is a way to
*pick* a colored state — their `Knobs` tables only list the original 9.

## Presets and the opts system

A "preset" resolves `(state, size)` to a `mode` name, a `speed`, and a fully-scaled `opts` map (`orbs::presets::resolve_preset`, `crates/core_engine/src/orbs/presets.rs`). Three sizes are shipped — **64, 32, 20** — pulled from upstream's `presets.ts` source directly rather than from `orbs-spec.json`, because at the time of porting the spec's `enums.sizes` only listed `[64, 20]` while the source already shipped a third. If the two ever disagree again, `presets.ts` (the actual source) wins over the derived spec file.

Scaling from a mode's base profile to a resolved preset follows three rules (`orbs::profiles`):
- **Count pairs** (`latRings`/`lonDensity`, `rings`/`lonDensity`, `lanes`/`segs`): each side scales by `sqrt(count)` so the *total* dot count scales by `count`.
- **Count keys** (`orbitN`, `ghostN`, `nodeN`, `strandN`, `signals`, plus `nodeCount` — the additive modes' name for `nodeN`, see [`parameters.md`](parameters.md)): scale linearly by `count`, except an explicit `0` stays `0` — a mode opting out of a layer (e.g. `ring` has no ghost sphere) must not have it resurrected as a single stray dot by rounding.
- **Radius keys** (`rBase`, `rDepth`, `ghostR`, `partR`, ...): scale linearly by `size`.

## API surface

`crates/core_engine/src/lib.rs` exports four functions (each with a native/UniFFI and a wasm/JSON variant — see [`architecture.md`](architecture.md#the-uniffi--wasm-bindgen-split)). All four dispatch across *every* family (`orbs`, `signal` — see [`signal.md`](signal.md) —, `ring` — see [`ring.md`](ring.md) —, `beacon` — see [`beacon.md`](beacon.md) — and `core` — see [`core.md`](core.md)) through one shared `resolve_any`/`render` path — no platform binding needs a second function name for a second family:

- **`frame(state, size, t)`** — resolves the stock preset and renders one frame. `t` is in seconds and **must already be multiplied by the resolved preset's `speed`** by the caller — see the callout below, this is the single most common integration mistake.
- **`frame_with_overrides(state, size, t, overrides)`** — same, but `overrides: HashMap<String, f64>` (a `Partial<Record<string, number>>` in TypeScript) is merged onto the resolved opts before rendering. Built for the Web Studio's live parameter sliders; nothing else needs it today, but it's the correct entry point for any future "tune this at runtime" use case rather than hand-rolling a second copy of `resolve_preset`.
- **`resolved_opts` / `resolved_opts_json`** — returns `{ mode, speed, opts }` for a `(state, size)` pair without rendering anything. Exists because `frame`/`frame_with_overrides` only return the rendered geometry, not the values that produced it — a caller building a slider UI has no other way to know where "no override" sits, or what `speed` to multiply `t` by.
- **`frame_transition(from_state, to_state, size, t, blend)`** — a real point-by-point morph between two states, `orbs`-only (see *State-to-state transitions*, below, for exactly which states and why).

### Pointer/touch scatter

`primitives::apply_pointer` (it moved out of `orbs::core` with the rest of
the family-agnostic pieces) is a mode-agnostic post-process, applied once at
the end of `render()` (the shared dispatch both `frame` and
`frame_with_overrides` call) rather than in any individual mode: if `opts`
carries a nonzero `pointerStrength` (plus `pointerX`/`pointerY`/
`pointerRadius`), every dot, line endpoint and polyline vertex within
`pointerRadius` of the pointer gets pushed outward with a squared ease-out
falloff. Dots and lines also fade slightly. Polylines only move: a polyline
carries one alpha for a whole ring or trace, and when that alpha was dimmed
the contact sheet showed the entire ring greying out, far from the cursor.
The push depends only on a vertex's position, so vertices shared between
elements stay attached. The motion is all
purely in the already-projected 2D `x`/`y` (not `z`, so `finalize_frame`'s
z-sort from whichever mode produced the frame stays valid). No preset ever
sets these keys, so plain `frame()` — and therefore every golden test — is
completely unaffected; it only activates when a caller opts in through
`frame_with_overrides`'s opts map, the same entry point the Studio's
sliders already use. This is why it works identically across all 18 states
without a single mode file changing: by the time `apply_pointer` runs, a
`Dot` is just an `x`/`y`/`r`/color record, indistinguishable from any other
mode's. **History, 2026-09-18:** until then only dots moved. The pointer
did nothing on the dot-less `ring`/`signal`/`core` frames. It also
*detached* `web`/`connecting` edges: under the pointer, 90 of 172 line
endpoints left their dots. With the fix, all 172 of 172 stay attached,
measured through wasm. Orb dot output is bit-identical before and after.

The Web Studio's `OrbCanvas`/`OrbStudio` wires this to real mouse/touch input
as a worked example: pointer *position* updates instantly every frame from
a ref (no easing needed there), but *strength* eases toward `0` or `1` over
~0.1s so entering/leaving the canvas doesn't pop the effect in/out
instantly. Deliberately kept out of `engineOverrides` (the per-state
slider state) since that object also feeds the code-export snippet, and
"wherever the mouse happened to be" has no business in exported code — it's
merged in only at the point of computing the live render.

**Wired into all three Studios.** Web does it in `OrbCanvas`/`OrbStudio`. The native Studios each have a touch handler that writes the same opts keys, with the same eased `pointerStrength`: `StudioModel.swift` and `StudioState.kt`. No platform-specific engine work was needed. Since 2026-09-18 the push also moves line endpoints and polyline vertices (see *History* above), so it registers on every family, not just orbs.

### Audio-reactive pulse

`primitives::apply_audio_reactive` is the audio equivalent of pointer
scatter, same shape and same location (a mode-agnostic post-process run
once at the end of the shared `render()`, not per-mode code): if `opts`
carries a nonzero `audioStrength`, it reads `audioLevel` (`0..1`, meant to
be a smoothed real-time volume reading — see [`audio-pipeline.md`](audio-pipeline.md)
for where that number actually comes from) and **breathes the whole frame
from its own centroid** — outward when `audioStrength` is positive, and
**inward when it is negative** (FX Spec 1.8's "inhale": the cue that reads
as *listening*, where speaking swells out). Brightness and radius follow
the magnitude in both directions, so an inhale is a tightening, not a
fade. The sign exists because with both states swelling outward, listening
and speaking measured the same on every pattern — measured in the
voice-state review. The centroid is computed from the dots
actually present rather than a hardcoded `size/2`, so it works for any
mode's geometry, including flat 2D ones. For a frame with no dots (every
`ring` state, the `signal` polyline styles, `core`'s shimmer) it falls back
to line endpoints and polyline vertices. Frames with dots keep the dots-only
centroid, so orb output is unchanged. Before 2026-09-18 such dot-less frames
returned early and never breathed. Polylines also get the dots'
radius/alpha glimmer (stroke width standing in for radius) rather than just scaling each dot's radius in place — a pure
size change reads as static; a position change reads as motion. `Line`
endpoints get the identical transform so line-based modes (`web`/`webflow`,
`crystallize`'s edges) don't visually detach from the dots they connect.
The position swell is deliberately the smallest-weighted of three cues
(position, radius, alpha) — a subtle glimmer-and-swell reads better than a
large, jarring displacement; a caller controls overall intensity via
`audioStrength`, these internal fractions just set the *balance* between
the cues.

Like pointer scatter: no preset sets `audioStrength`, so plain `frame()`
and every golden test are unaffected; it activates only when a caller
opts in via `frame_with_overrides`. The Web Studio's Orb panel wires this to
a real Web Audio pipeline (mic or a synthesized test tone) as a worked
example — see [`audio-pipeline.md`](audio-pipeline.md) for the full
architecture, including why the *audio capture and FFT extraction* itself
is NOT shared code the way this scaling math is (Web Audio API vs. iOS's
`AVAudioEngine`+vDSP vs. Android's `AudioRecord`/`Visualizer` are
genuinely separate per-platform implementations that only converge at this
function's `{audioLevel}` input).

`orbs::modes::spectrum` (`speaking`) additionally reads real per-band data
directly (`audioBand0..N`, via the shared `primitives::audio_band` helper)
to drive its bar heights, instead of (or alongside) this generic pulse —
see that mode's own tests for the fallback-to-synthetic-pattern behavior
when no real audio is supplied. `signal::modes::bar` (see
[`signal.md`](signal.md)) uses the same `audio_band` helper and the same
indexed-key encoding.

### Ink (whole-visual opacity)

`primitives::apply_ink` (FX Spec 1.8) multiplies the alpha of every dot,
line, polyline and fill by `ink` (`0..1`, default `1`). It runs **after
`apply_glow`**, so halos fade with their source and a faded visual fades as
one thing, and **before** the interrupt flash and the mute cue, so those two
events still read at full strength on a visual resting at low ink. Opacity
only: no geometry change and no ink/lightness shift, which is what keeps it
mode-agnostic. A no-op at `1`, so plain `frame()` and both golden sets are
unaffected. It exists because "how present is this visual right now" is a
state cue — an assistant rests below full ink when idle and comes to full
ink when it listens — and faking it outside the engine (CSS opacity) was
something no native view or export could reproduce.

### Mute / error cue

`primitives::apply_muted` is the third mode-agnostic post-process, run
last in `render()` (after the two above): if `opts` carries `muted > 0`
(`0..1`) it dims, lightens, desaturates (or tints toward `mutedHue` when
`mutedTint > 0`) and slightly deflates every dot, line and polyline —
geometry untouched. Built for `signal` (the "mic muted / connection lost"
cue every voice product needs) but, being a post-process, it works on all
18 `orbs` states too. Like the other two: no preset sets it, so plain
`frame()` and every golden test are unaffected. Slowing the animation
while muted is deliberately the caller's job (scale your clock, the way
`t * speed` already is) — see [`signal.md`](signal.md#muted-the-mute--error-cue-an-opts-flag-not-a-state)
for why scaling `t` inside a stateless engine would jump on toggle.

### Interrupt / barge-in flash

`primitives::apply_interrupt` is the fourth post-process, run between the
audio pulse and the mute cue: a **one-shot** flash for the moment a user
starts talking over the agent. That moment is a real, named server event
on both major realtime voice APIs (fetched):
OpenAI Realtime's
`input_audio_buffer.speech_started` (the server "will automatically cancel
any in-progress model response", then `response.cancelled`) and Gemini
Live's `serverContent.interrupted` — and Gemini exposes *only* that single
signal, no VAD start/stop pair, so the contract is "a moment fired". The
caller passes `interruptAge` (seconds since that moment on its own wall
clock — an **age, not a timestamp**, because `t` is pre-scaled by each
state's `speed` and a timestamp would force the caller to know that), plus
optional `interruptDuration` (0.45s), `interruptStrength`, `interruptTint`/
`interruptHue`. With `k = strength · (1 − age/duration)²`: contrast up
(ink toward 0), alpha and radius/stroke swell, and a short outward kick
from the frame's own centroid — taken over dots, line endpoints *and*
polyline vertices, so a polyline-only `signal` frame flashes too. No-op
without the key or past the duration, so `frame()` and the golden suite
are unaffected. Both Studio panels have an "Interrupt" button that fakes
the event; a real adapter sets the timestamp from the events above.

**This is probably a `beacon` behavior in waiting.** A one-shot,
attention-grabbing, decaying event is that family's exact definition in
the product plan; when `beacon` exists this should either move there or
be wrapped by it. It ships here now because the event is real today and
`beacon` isn't.

### Pulse and decay: shared Energy/State envelopes

Two more post-processes, `primitives::apply_pulse` (right after the audio
pulse, before the materials) and `primitives::apply_decay` (after the
interrupt flash, before the mute cue), so the full chain is `pointer →
audio → pulse → noise → gradient → glow → interrupt → decay → muted`.
Before these, periodic breathing and one-shot fades were rewritten per
mode; now any state in any family can wear them, with no preset set and
no golden vector affected (absent key = frame untouched).

- **`apply_pulse`** — `pulseStrength` (`0..1`, the gate), `pulsePeriod`
  (2 s of **real time**: `render` divides the preset speed out of `t`, like
  `noiseSpeed`, `particleLife` and `holoSpeed`; a spec's own `speed` still
  scales it — see materials.md *Material time*),
  `pulseOpacity` (0.5), `pulseScale` (0), `pulsePhase` (0). The curve is
  Tailwind's `animate-pulse` (`50% { opacity: .5 }`, 2s,
  `cubic-bezier(0.4, 0, 0.6, 1)`), exposed as `primitives::pulse_wave`.
  The two depth knobs follow SF Symbols 6's split (WWDC24 "What's new in
  SF Symbols 6"): **Pulse** "conveys ongoing activity by changing its
  opacity", **Breathe** "uses opacity and size" — `pulseScale 0` is the
  former, `> 0` swells positions, radii and strokes about the frame's
  centroid (dots, line ends and polyline vertices, so `signal` breathes
  too). Stateless: a pure function of `t`.
- **`apply_decay`** — `decayAge` (seconds since the event on the caller's
  wall clock, the same contract as `interruptAge` for the same reason;
  absent = no-op, negative = not yet), `decayDuration` (0.6s),
  `decayCurve`, `decayScale` (0; how far it shrinks toward the centroid
  by the end). Alpha × envelope on every element; from `decayDuration`
  on, the frame comes back **empty**. The envelope is the shared
  `primitives::decay_envelope(age, duration, curve)`: `0` linear, `1`
  quadratic ease-out `(1 − u)²` (default, exactly `apply_interrupt`'s
  curve), `2` exponential — Web Audio's `setTargetAtTime`
  (`e^(−t/τ)`, 95% after 3τ) with `τ = duration/3`, renormalised to hit 0
  at `duration` — and `3` Material 3's exit curve
  `EasingEmphasizedAccelerate` `cubic-bezier(0.3, 0, 0.8, 0.15)`
  (androidx `MotionTokens.kt`), which holds and then drops away.

**What was deduplicated, and what deliberately wasn't.** Only call sites
whose math was *identical* moved onto the shared helpers — `beacon`'s
`reconnecting` dip now calls `pulse_wave`, `apply_interrupt`'s envelope
calls `decay_envelope(…, DECAY_QUAD)` and its centroid the shared
`frame_centroid` — so their output is bit-for-bit unchanged (their
existing tests are the check). `hush`'s sine breathing, `sonar`'s
half-sine brighten-then-fade and `ping`'s Tailwind *ping* curve are
different shapes on purpose, tuned by eye, and were left alone.

### Color system: ink vs fixed, and line colour

**Paint contract, updated 2026-09-18:**
- **`Line` has `saturation`/`hue`**, with the same semantics as `Dot` and
  `Polyline`. Every mode emits 0, which is exactly the old grey. The four
  mode literals (`web.rs`, which is a ported file and got a two-line
  mechanical edit; `webflow.rs`, `crystallize.rs`, `warp.rs`) pass `0.0`,
  and `golden.rs` proves `web` is unchanged. Colour arrives only through
  post-processes: `apply_color`, `apply_gradient`, glow tint, muted and
  interrupt now treat lines like polylines.
- **`OrbFrame.colorMode`** is `ink` (default) or `fixed`. It is a
  UniFFI enum `ColorMode`; wasm JSON has `"colorMode": "ink" | "fixed"`.
  Renderers resolve lightness as
  `L = (dark && colorMode == ink) ? 1 − white : white`. The background
  stays themed either way.
  - `ink` is the original behaviour: grey ink and depth ramps read the
    right way round in both themes.
  - `fixed` keeps `white` as-is in both themes. The name and meaning come
    from Material 3's *fixed* colour roles, which "maintain the same tone
    in light and dark themes" (androidx `ColorScheme.kt`).
  - It is frame-level rather than per-element: `apply_color` recolours
    the whole frame, and a renderer needs one branch.
- Implemented in every renderer and exporter:
  - the Web Studio's `drawFrame.ts` + `export/image.ts`
  - `OrbCanvasView.swift` + `ImageExport.swift`
  - `OrbCanvas.kt` + `ImageExport.kt`

  The RN bridges (`SinuaCore.swift`, `SinuaCoreModule.kt`) pass
  line colour and `colorMode` through, and the TS types gained both.
- Set by `apply_color`'s `colorMode` opt. The full key table is in
  [`materials.md`](materials.md#color-one-colour-for-the-whole-frame-design-notes-2026-09-18).

### Paint contract: fills and effects (materials phase 1, 2026-09-18)

The user chose the vector path, with no shader tier. The paint contract gains **one primitive and two effects**, all of which can be drawn the same way on Canvas 2D, SwiftUI `GraphicsContext`, Compose and SVG. voice-adapters implements the painters; the contract is agreed with them.

- **`Fill`**: a closed polygon (the engine tessellates arcs, as it does for polylines) with the same ink as a `Dot` (`white` / `a` / `saturation` / `hue`, mirrored on dark unless `colorMode` is `fixed`).
  - Optional `gradient: FillGradient`:
    - `kind` 0 = **linear** (x0, y0) → (x1, y1); `kind` 1 = **radial**, centre (x0, y0), radius 0 → `r`;
    - pad beyond both ends;
    - 2–3 `GradientStop`s, sorted by `offset` in 0..1.
  - A stop's painted alpha is **`stop.a × fill.a`**. Stops carry relative alpha, and pulse, decay, mute and cross-fades only ever touch `fill.a`. The solid ink stays as the fallback.
  - **No conic gradient**: SwiftUI's `GraphicsContext` conic shading is iOS 18+ (this package targets 15), and SVG has none.
- **Effects**:
  - `blur` is a Gaussian **σ in engine units** (0 = none);
  - `blend` is 0 normal / **1 additive** (Canvas `lighter`, Baseline since 2015; SwiftUI `plusLighter`, iOS 15; Compose `BlendMode.Plus`, which is `PorterDuff.ADD` below API 29);
  - a fill carries its own `blur` / `blend`;
  - on dots, lines and polylines they come as frame-level **`EffectRun { target (0 dots / 1 lines / 2 polylines), start, count, blur, blend }`**, so the existing records are untouched. Today only real-blur glow uses runs.
  - Additive brightens, so it is **invisible on a light background** (dark ink added to white paper stays white). It is a dark-theme effect; use normal blend on light themes.
- **Draw order:** **fills → polylines → lines → dots**, each in engine order. Effects never reorder.
- **Blur on each renderer:**
  - Web uses the `shadowBlur` technique (σ = shadowBlur/2). Canvas `ctx.filter` is not Baseline: Safari ships it "disabled by default".
  - SwiftUI uses `addFilter(.blur(radius:))` (iOS 15).
  - Compose uses `BlurMaskFilter` per element. Where that isn't reliable (below ~API 29) the element draws unblurred.
  - The engine-side fallback is `blurScale` 0: every σ goes to 0, and glow's blur mode falls back to its stacked copies.
- **Byte identity:** `OrbFrame.fills` / `.effects` are left out of JSON when empty, and the packed transport stays v1 unless a frame has either (v2 layout: [`platforms/web.md`](platforms/web.md)). Every frame without the new opts is byte-for-byte what it was: 214 golden cases diff-checked, plus the 1.0 / 1.1 / 1.2 spec locks.
- **Tolerance:**
  - Geometry, including fills and runs, is golden-exact (four new sinua cases).
  - Pixels are "the same within tolerance" across platforms: composite over the theme's paper, then mean |ΔRGB| ≤ 2/255 and p99 ≤ 24/255. This is voice-adapters' metric, on those same four golden cases.
- **Phase 2 (liquid, 2026-09-19): `Fill.holes: [[Point]]`.** These are inner rings, painted as **one path with the even-odd rule** together with `points`: Canvas `fill(path, "evenodd")`, SwiftUI `FillStyle(eoFill: true)`, Compose `PathFillType.EvenOdd`, SVG `fill-rule="evenodd"`.
  - Winding doesn't matter, and the engine doesn't guarantee any.
  - Left out of JSON when empty. Packed **v3** only when some fill has holes.
  - The liquid material is the first to produce holes ([`materials.md`](materials.md#liquid-metaball-contours-materials-phase-2-2026-09-19)).
- **Naming:** these are **effects**, paint instructions. What the engine computes into primitives is a **material** (see the top of [`materials.md`](materials.md)).
- **Where it's used today:**
  - liquid `liquidStyle` 0 (fills with holes)
  - `shimmer` `highlightFill` ([`core.md`](core.md))
  - `radar` `trailFill` ([`beacon.md`](beacon.md))
  - glow `glowMode` 1 / `glowBlend` 1 ([`materials.md`](materials.md))

### Per-vertex stroke colour (2026-09-19)

`Polyline.hues` holds one hue per point, or is empty (the old single `hue`). `apply_gradient` and `apply_holo` set it whenever a stroke's vertex hues differ, so rings, beacons and signal traces sweep along their length. `white`, `a`, `w` and `saturation` stay uniform. `hue` keeps its old value, the vertex-mean sample, and is the fallback for any renderer without per-vertex paint.

**Paint rule** (voice-adapters' painters, studio-ui-ux's canvases and exporters):
- each segment `i-1 → i` is a round-capped stroke of width `w`, with a linear gradient from `ink(white, saturation, hues[i-1])` to `ink(…, hues[i])` at **alpha 1**;
- a zero-length segment is a round dot of diameter `w` in vertex *i*'s colour;
- all segments go into **one offscreen/transparency layer**, composited once at `a`, with the element's effect run (blur, blend) applied at that composite:
  - Canvas: a scratch canvas + `drawImage` with `globalAlpha` / `filter` / `globalCompositeOperation`;
  - SwiftUI: `drawLayer` + opacity (or CG `beginTransparencyLayer`);
  - Compose: `saveLayer` with alpha;
  - SVG: `<g opacity>` + per-segment `<linearGradient gradientUnits="userSpaceOnUse">`.

**Why a layer:**
- There's no stroke-following gradient on any target. Skia's developers point at per-segment gradients or `drawVertices` (skia-discuss, "How to paint gradient color following a stroke path?"); Canvas2D, CoreGraphics and SVG have no mesh primitive.
- Compositing the segments directly would double-paint the round-cap overlaps at `a < 1`. That's the notch problem `Polyline` was introduced to fix. Inside an opaque layer the overlaps don't show.

**Interpolation between vertices** uses the renderer's own gradient (sRGB). Vertices are dense, and RGB interpolation handles a 359 → 1 wrap by itself.

**The user kept HSL over OKLCH** from an A/B (2026-09-19). There's no colour-space code in the engine.

**Transport:**
- JSON leaves `hues` out when empty.
- Packed **v4** only when some polyline has `hues` (layout: [`platforms/web.md`](platforms/web.md)).

**Cost:** a per-vertex stroke counts as `n − 1` extra elements (its segment strokes).

**Golden 1.6.0:**
- the only old case that changed is `completing-64-0.6-holo-glow`, which gained `hues` only;
- 4 new cases.

### Materials: glow / noise / gradient

Three more post-processes, `primitives::apply_noise` → `apply_gradient` →
`apply_glow`, run between the audio pulse and the interrupt flash. They
are the engine's **materials** — the Glow/Noise/Gradient layer
the product's parameter plan
asks for, built as exactly this kind of opts-activated, family-agnostic
step rather than as modes or a family: `glowStrength` splices layered
Gaussian-falloff halos in behind every dot/line/polyline (the CSS
layered-shadow fake, since no renderer here has blur), `noiseStrength`
jitters every vertex by a slow `perlin3` field (Nature of Code's walker,
edges staying attached to their dots), `gradientStrength` recolors every
element along a CSS-convention linear ramp across the frame (`0deg` up,
`90deg` left→right). Same rule as the four above: no preset sets any of
their keys, so plain `frame()` and every golden test are unaffected. Keys,
defaults, chain order and sources: [`materials.md`](materials.md).

### State-to-state transitions

`frame_transition(from_state, to_state, size, t, blend)` does a real
point-by-point morph, but **only** between `glowing`, `calibrating`, and
`progressing` — the one trio that happens to place point `i` of `nodeCount` at
the exact same `fib_dir(i, nodeN)` direction (`aurora`/`chladni`/`eclipse`
were deliberately built on the same lattice; see
`orbs::modes::transition`'s header for the full reasoning, including why
no `slerp` is even needed here and why depth-shading still uses each
mode's own camera while final position uses one shared, blended camera).
Returns `None` for any other pair — there's no point correspondence
between, say, `orbits`' particles and `crystallize`'s 12 vertices, so no
per-point blend would be meaningful. A caller should fall back to
cross-dissolving two independent `frame()` calls for those pairs, which
works for all 18 states uniformly since it never looks inside either
frame's data — the Web Studio's `TransitionPanel` does exactly this,
picking whichever technique applies automatically and labeling which one
is active.

`t` here is plain elapsed seconds, not scaled by either endpoint's
`speed` — the two states have different tuned speeds and there's no
obviously-right choice between them for a transition preview, so this
keeps it simple rather than guessing.

### The `t * speed` callout

None of the mode functions read a `speed` key from `opts` — `speed` is a **separate field** on the resolved preset (`Resolved.speed`), and every mode's own internal timing constants (e.g. orbits' `t * 0.12` orbital rate) assume the `t` they're handed has already been scaled by it. Concretely:

```
t = elapsedSeconds * resolvedOpts(state, size).speed
frame(state, size, t)
```

**This bug shipped once already** — both `apps/smoke` and the first draft of the Web Studio called `frame()` with raw elapsed seconds, meaning every state animated at the same rate regardless of its tuned `speed` value. Caught by eye (states that should look visibly faster/slower didn't), not by a test, because nothing asserts *animation rate* — only per-frame geometry at a given `t`. Both were fixed; if you add a fourth caller of `frame`/`frame_with_overrides` with a live clock, apply this multiplication or it will silently under/over-speed every state uniformly.

### Cost estimate

`estimate_cost(state, size, overrides)` and `fx_spec_cost(json, state, inputs, low_power)` return `FxCost`. On the web they are `estimateCost` / `fxSpecCost`; UniFFI and RN expose the same names.

`FxCost` is a **render-cost proxy, not a measurement**:
- `elements` = dots + lines + polylines, the draw calls a canvas renderer issues (a per-vertex-hue polyline adds `n − 1` for its segment strokes, 2026-09-19);
- `coverage` = total primitive area / canvas area, an overdraw proxy: 1.0 = the canvas painted once;
- the breakdown (`dots`, `lines`, `polylines`, `points`);
- `baseElements` / `baseCoverage` for the same object with every material off (glow, noise, pulse, gradient and, since 2026-09-19, liquid), so the difference is what the materials add;
- a `class`:

| class | rule |
|---|---|
| `heavy` | elements > 1600 **or** coverage > 3.0 |
| `medium` | elements > 700 **or** coverage > 1.0 |
| `light` | otherwise |

**Materials phase 1 additions:**
- fills count as elements, with their polygon (shoelace) area in `coverage`;
- a new **`blurLoad`** = Σ over blurred elements of (bounding box grown by 3σ on each side) × σ, divided by the canvas area. A Gaussian's cost grows with the area it touches and with its radius; per-call overhead is already `elements`' job;
- the class also goes `medium` above 2.0 and `heavy` above 5.0.

The blur bounds come from the blur-glow column of `cost_distribution` at size 64:

| states | blurLoad |
|---|---|
| orbs | 0.04–1.99 |
| signal | 2.8–3.75 |
| rings / beacons (few but large blurred strokes) | 5.7–12.5 |
| shimmer | 31 |
| `locating` (one canvas-sized halo) | 103 |

It is the maximum over four fixed sample times, so a badge doesn't flicker as an animation breathes. The thresholds come from the distribution over every state at size 64 (`cargo test -p core_engine cost_distribution -- --ignored --nocapture`):
- Without glow, no state exceeds 566 elements or 0.38 coverage, so all are `light`.
- With full glow, element counts cluster at ≤ 690, 817–932, 1171–1277 and 2028–2606, and the bounds sit in the gaps.
- On the Web, the heavy cluster is also where the old JSON transport cost 3–4.4 ms per frame (see [`platforms/web.md`](platforms/web.md#frame-transport-packed-float64array-2026-09-18)).

Paint cost still depends on renderer, device and output resolution. The class tells you *relative* weight and what to shed first (`base*`), not frame time.

## Other families considered

Before committing to porting more `orbs` modes, three other packages from the same upstream author's repo were evaluated as second-family candidates and explicitly deferred (not rejected — just not started):

- **`border-beam`** — has the same mature port infrastructure (`spec/`, `ports/ios`, `ports/react-native`) as `thinking-orbs`, but its actual "engine" is a single cosine ping-pong oscillator driving CSS custom properties. Low Rust-sharing value; the rendering (CSS gradients) doesn't map cleanly to a shared native primitive the way dot/line geometry does.
- **`liquid-gooey`** — genuinely different math (spring physics + 2D metaball/silhouette blending), which would be a much better test of the family-pattern's generality. But upstream has **no** `spec/`/`ports/` for it at all — no frozen golden vectors to port against, meaning a port would have no independent correctness proof, unlike everything built so far.
- **`metal-fx`** — GPU shader (WebGL/Metal) based. Shaders are authored per graphics API regardless of what drives their uniforms, so the Rust-sharing value is the lowest of the three.

If a second family gets picked up, re-read this section first — the tradeoffs may have changed (e.g. upstream may have since shipped a `liquid-gooey` port with golden vectors).
