# Lessons learned

Concrete things that went wrong (or almost did) while building this, kept here so they don't get rediscovered the hard way. Several are cross-referenced from the docs where they're most relevant; this page exists so a "why does X work this way" search has one place to check first.

## Engine / porting

**A real transcription bug, caught before it shipped.** `orbs::modes::rubik`'s scramble-cycle easing originally computed `cl` as `p.min(1.0) / 0.7` — a straight character-by-character misreading of the TypeScript source's `Math.min(1, p / 0.7)`, which divides *then* clamps, not the other way around. Caught by re-reading the diff against the TS source before running the golden test, not by the test itself (the test would have caught it too, on `solving`/`rubik` specifically — this just found it one step earlier). The general lesson: line-by-line porting is exactly the kind of task where a small, easy-to-miss operator-precedence-shaped bug survives a plausible-looking diff; re-reading against the source is worth the time even when a test suite exists as a backstop.

**The z-sort tie-break problem** — a cross-platform floating-point non-determinism in a near-degenerate sort key, not a real bug. Full writeup: [`testing.md`](testing.md#the-z-sort-tie-break-problem).

**`t * speed` is the caller's job, not the engine's.** Shipped as a bug once (both `apps/smoke` and the Web Studio's first draft). Full writeup: [`engine.md`](engine.md#the-t--speed-callout).

**A curve drawn as consecutive independent `Line`s always shows its seams.** `signal`'s first `waveform` was ~48 `Line` segments; every renderer strokes each one as its own butt-capped path, so every bend showed a wedge gap on the outside and a double-painted notch on the inside — a "caterpillar," visible at any point count and worse at alpha < 1. Not fixable by adding points or by any renderer tweak that keeps per-segment strokes; it needed a primitive that *is* one stroke with round joins (`primitives::Polyline`). Diagnosed by rendering real frames to PNG through the wasm package in Node and zooming in, not by reading code — the code looked fine. Full writeup: [`signal.md`](signal.md#the-polyline-primitive-why-signal-needed-one).

## Rust / FFI

**`rust-toolchain.toml`'s pinned channel is a separate toolchain installation.** `rustup target add <target>` without `--toolchain <version>` silently adds to the *default* toolchain, not this repo's pinned one — a build then fails with "can't find crate for `std`" even though `rustup target list --installed` (unqualified) looks fine. Always check `--installed --toolchain <pinned-version>` specifically when debugging this. Full context: [`development.md`](development.md#rust-all-platforms-need-this).

**`panic = "abort"` would have silently broken UniFFI.** Considered for the release profile (smaller binaries, standard advice for FFI libraries) and rejected: UniFFI wraps every exported call in `catch_unwind` to turn a Rust panic into a safe error at the FFI boundary instead of aborting the host process — `catch_unwind` is a no-op under `panic = "abort"`, so this would have silently defeated that safety net rather than erroring loudly. Left as a comment in the workspace root `Cargo.toml`'s `[profile.release]` rather than just omitted, so it doesn't get "optimized" back in later without someone reading why.

**UniFFI and wasm-bindgen cannot coexist in the same compiled target.** Not a bug so much as a hard constraint that shapes `crates/core_engine`'s whole `Cargo.toml`: `uniffi` is a target-specific dependency (`[target.'cfg(not(target_arch = "wasm32"))'.dependencies]`), not a normal one — it does not compile for `wasm32-unknown-unknown` at all. Every function needs a `#[cfg_attr(not(target_arch = "wasm32"), uniffi::export)]` native path and a separate `#[wasm_bindgen]` path inside a `#[cfg(target_arch = "wasm32")] mod wasm { ... }` block. See [`architecture.md`](architecture.md#the-uniffi--wasm-bindgen-split).

## Native bridges

**Swift's `[String: Any]` / `NSDictionary` don't preserve or expose key order the way JS objects and Rust's `serde_json` do.** Broke a naive `JSON.stringify` equality check, and separately broke a naive `for (key, value) in nsDictionary` iteration (silently zero entries instead of a type error). Full writeup: [`testing.md`](testing.md#two-more-comparison-fragility-bugs-found-the-same-way).

**`xcrun simctl launch` on an already-running app does not restart it with a freshly installed binary — it just foregrounds the existing process.** Cost real debugging time: a fix was made, rebuilt, reinstalled, relaunched, and appeared not to work — because the *old* process was still running and `simctl launch` brought it back to the foreground instead of starting the new one. Always `xcrun simctl terminate <udid> <bundle-id>` before `install` + `launch` when iterating on a native fix, not just before the first install.

**Cross-package relative paths silently don't resolve once a package is consumed through `node_modules` autolinking.** `packages/react-native`'s Android Gradle module originally referenced `packages/android`'s generated Kotlin/`.so` output via a relative `../../android/src/main/...` path in `sourceSets` — worked when built standalone, failed (`Unresolved reference 'uniffi'`) once consumed by the example app through its symlinked `node_modules` entry, because that path resolves differently inside an "included Gradle build" behind a symlink than a normal same-repo relative path does. Fixed by having `build.sh` **copy** the artifacts in instead of referencing them — the same fix applied to the iOS side pre-emptively once the pattern was clear. See [`react-native.md`](platforms/react-native.md#package-layout).

**Metro needs `watchFolders` for a `file:`-linked sibling package**, the same way Vite needs `server.fs.allow` for one — neither dev server watches or resolves outside its project root by default, even through a symlink. See [`web.md`](platforms/web.md#consuming-it-from-another-local-package) and [`react-native.md`](platforms/react-native.md#the-example-app).

**A long-running Metro instance can quietly wedge** (bundling gets stuck at a fixed percentage, `[timeout] connection terminated ... after not responding for 60 seconds` repeating) after enough reload cycles across a debugging session. No root cause was chased down — killing and restarting with `--reset-cache` reliably fixed it. If a rebuild appears to have "no effect" and the app hasn't been visibly relaunched, check Metro's own log before assuming the native fix is wrong.

## Web tooling

**wasm-pack writes `pkg/.gitignore` = `*`, and `npm pack` honours it.** `@devin-fx/core` listed `pkg` in `files`, and the repo's own tests all passed. They ran against the working tree, so nothing noticed that the packed tarball contained no wasm (found 2026-09-20 while installing it into an Angular app). The build now deletes that file, and `test/pack.test.mjs` checks `npm pack --dry-run`. Test the tarball, not the folder. And test a *production* bundle, run: wasm-pack's `pkg/package.json` `sideEffects` list let Rollup/esbuild tree-shake the inline init away, and neither the Vite dev server nor a green `vite build` showed it (`packages/core/bundler-check/`).

**`wasm-pack --target bundler` output needs `vite-plugin-wasm` for `vite build` (production), not just the dev server.** Vite's dev server handles the ES-module-wasm-import pattern natively; the Rollup-based production build does not, and fails with `[vite:wasm-fallback] "ESM integration proposal for Wasm" is not supported`.

**A change to `crates/core_engine`'s output shape blanks the Web Studio until `packages/core` is rebuilt.** The Studio imports `@sinua/core` through a `file:` symlink, and that package's `pkg/*.wasm` is build output, not source — so after `Polyline` was added to `OrbFrame`, a Studio whose wasm predated it crashed on load with `frame.polylines is not iterable` (the TS types said the field existed; the stale binary didn't emit it). Found by the `studio-ui-ux` session, not by the session that made the change. Rule: any edit under `crates/core_engine/src/` that touches `primitives.rs`/`lib.rs` (a new field, record, or export) must be followed by `npm run build` in `packages/core`; the running Vite dev server then picks the new wasm up without a restart. Same family of problem as the stale-`pkg/` note in [`platforms/web.md`](platforms/web.md#consuming-it-from-another-local-package), one level down.

**`vite-plugin-top-level-await` errored internally** (`missing field 'type'`, inside its SWC-based transform) in this toolchain's exact dependency versions. Rather than chase a version pin, `build.target: "esnext"` in `vite.config.ts` sidesteps needing the plugin at all — esbuild only rejects top-level `await` for pre-2022 targets, and nothing in this project needs to support one.
